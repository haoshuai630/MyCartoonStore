# 10 · 任务清单与增量汇报规范

> 从 M01 起执行：**先写任务清单 → 逐任务实现 → 每完成一个任务写一份汇报与逐行分析 → 提交并推送到 GitHub**。
> 本文件是流程约束，与 09 篇的模块级 DoD 配合使用。

---

## 1. 为什么要拆到"任务"

模块（M01 数据库与实体）仍然太大，一次做完才能验证，中间出错很难定位，也没法回答"今天做完了什么"。

拆成任务后：

- 每个任务 ≤ 2 小时，能独立验证，能独立回滚；
- 每个任务一个 commit、一份汇报，历史可读；
- 汇报里的"逐行分析"只覆盖本任务新增的代码，篇幅可控。

---

## 2. 模块启动前：任务清单

**规则：任务清单必须先提交进仓库，再写第一行业务代码。**

位置：`docs/tasks/Mxx-<模块名>-任务清单.md`

每个任务必须写清六项：

| 字段 | 说明 | 不合格示例 |
|---|---|---|
| 编号 | `Mxx-yy` | 用"第 1 步"代替编号 |
| 目标 | 一句话说清产出什么 | "完善数据库" |
| 产出 | 具体文件路径 | "相关文件" |
| 验收 | 可执行的验证命令或检查点 | "看起来对了" |
| 依赖 | 前置任务编号，或"无" | 留空 |
| 预估 | 小时数 | 不估 |

粒度要求：

- 一个任务只动一个关注点（只改 SQL、或只加实体、或只加测试）；
- 验收必须能跑（命令、SQL 查询、测试用例）；
- 超过 2 小时就继续拆。

---

## 3. 任务执行：小步提交

每个任务的固定顺序：

```
① 写代码/脚本
② 验证（命令、SQL、测试）
③ 写 reports/Mxx-yy-<任务名>.md
④ git add + commit
⑤ push 到 GitHub
⑥ 在任务清单里把该任务标记为 ✅
```

- **一个任务一个 commit**，不做"攒一批再提交"。
- 提交信息格式：`feat(m01-02): 生成分类与商品种子数据`
- 清单勾选放在同一个 commit 里，保证清单与代码同步。
- 推送失败不阻塞下一个任务，但必须当天补推。

---

## 4. 增量汇报

位置：`reports/Mxx-yy-<任务名>.md`，模板见 [`templates/增量汇报模板.md`](templates/增量汇报模板.md)。

固定结构：

1. 任务信息（编号、commit、日期、状态）
2. 这次做了什么（一段话，说人话）
3. 产出文件（表格：路径 / 行数 / 作用）
4. 逐行分析（本任务的核心代码或 SQL）
5. 验证结果（命令 + 实际输出）
6. 遗留问题
7. 下一个任务

篇幅：1–2 页。宁可短而准，不要长而空。

---

## 5. "逐行分析"到底逐到什么程度

不同类型的产物，要求不同：

| 产物 | 要求 |
|---|---|
| Java 核心逻辑（Service、状态机、事务方法、校验） | **逐行**：行号 / 代码 / 为什么这么写 |
| 自定义 SQL（扣库存、行锁、版本更新、分页查询） | **逐行**：语句 / 作用 / 为什么不用另一种写法 |
| 实体、DTO、Mapper 接口 | 逐字段/逐方法说明，**不逐行** |
| 建表 DDL | 逐列说明约束来源（与课程 SQL 对齐） |
| 大批量 INSERT 种子数据 | **按语句块 + 规则**说明，不逐行贴数据 |
| 配置、pom | 只说明改了什么、为什么 |

判定标准：**读者能不能据此判断"这行代码非写不可"**。写不出来的行，就不是核心行。

---

## 6. 模块收尾

一个模块的所有任务完成后：

1. 写模块总汇报 `reports/Mxx-<模块名>.md`：目标、架构位置、任务清单完成情况、验收对照、遗留问题、下一步。
2. 打 tag：`v0.<n>-m<xx>`。
3. 更新 `reports/README.md` 的进度表。

模块总汇报 **不重复**各增量汇报的逐行内容，只做汇总与交叉引用。

---

## 7. 每个任务的完成定义（DoD）

- [ ] 验收命令实际执行过，输出写进汇报
- [ ] 新增/修改的代码有对应测试，或说明为何不需要
- [ ] 汇报已写，行号与本次提交一致
- [ ] 任务清单已勾选
- [ ] 已 commit 并 push

任一条不满足，任务视为未完成，不进入下一个任务。

---

## 8. 与 GitHub 的关系

- **模块分支开发**：每个模块开 `feat/mxx-*`，任务 commit 进分支并**当天推送**，`main` 始终保持可运行。
- **通过测试才合并**：模块全部任务完成、`mvn verify` 全绿、模块总汇报写完，才合并回 `main` 并打 tag。
- 单人项目不强制 PR，但合并前必须自己跑一遍模块测试。
- 任务清单与汇报都在仓库里，答辩时按 `reports/` 目录就能讲清开发过程。
- 不补造提交历史；合并用 `--no-ff` 保留模块边界。
