# 10 · 任务清单与增量汇报规范

> 从 M01 起执行：**先写任务清单 → 逐任务实现 → 每完成一个任务写一份汇报与逐行分析 → 提交并推送到 GitHub**。
> 本文件是流程约束，与 09 篇的模块级 DoD 配合使用。

---

## 1. 为什么要拆到"任务"

模块（M01 数据库与实体）仍然太大，一次做完才能验证，中间出错很难定位，也没法回答"今天做完了什么"。

拆成任务后：

- 每个任务 ≤ 2 小时，能独立验证，能独立回滚；
- 每个任务一个 commit、一份汇报，历史可读；
- 汇报里的"逐行分析"只覆盖本任务新增的代码，篇幅可控。

---

## 2. 模块启动前：任务清单

**规则：任务清单必须先提交进仓库，再写第一行业务代码。**

位置：`docs/tasks/Mxx-<模块名>-任务清单.md`

每个任务必须写清六项：

| 字段 | 说明 | 不合格示例 |
|---|---|---|
| 编号 | `Mxx-yy` | 用"第 1 步"代替编号 |
| 目标 | 一句话说清产出什么 | "完善数据库" |
| 产出 | 具体文件路径 | "相关文件" |
| 验收 | 可执行的验证命令或检查点 | "看起来对了" |
| 依赖 | 前置任务编号，或"无" | 留空 |
| 预估 | 小时数 | 不估 |

粒度要求：

- 一个任务只动一个关注点（只改 SQL、或只加实体、或只加测试）；
- 验收必须能跑（命令、SQL 查询、测试用例）；
- 超过 2 小时就继续拆。

---

## 3. 任务执行：小步提交

每个任务的固定顺序：

```
① 写代码/脚本
② 验证（命令、SQL、测试）
③ 写 reports/Mxx-yy-<任务名>.md
④ 审阅：把 `reports/Mxx-yy-<任务名>.md` 作为文档交给负责人审阅，等人确认
⑤ 确认后：勾选任务清单 + git add + commit
⑥ push 到 GitHub
```

**④ 是硬门槛**：没有确认就提交，视为流程违规，需要回滚重做。
汇报被要求修改时，改完重新贴出来再审一次，不带着"待改"提交。

- **一个任务一个 commit**，不做"攒一批再提交"。
- 提交信息格式：`feat(m01-02): 生成分类与商品种子数据`
- 清单勾选放在同一个 commit 里，保证清单与代码同步。
- 推送失败不阻塞下一个任务，但必须当天补推。

---

## 4. 增量汇报（两份文档）

每个任务产出**两份 Markdown**：

| 文件 | 作用 | 篇幅 |
|---|---|---|
| `reports/Mxx-yy-<任务名>.md` | 汇报：做了什么、产出、验证、遗留、下一步 | 1–2 页 |
| `reports/Mxx-yy-逐行验收.html` | **逐行对照**：行号连续、左列源码、右列说明，悬停联动高亮 | 不限，按代码量 |

逐行验收 HTML 由 `db/tools/gen_acceptance.py` 生成，不手工维护；说明取自代码内的 `EXPLAIN` 字典与数据行解析规则，改代码后重跑即可。格式对齐课程模板：空行渲染为 `gap` 行、注释行绿字、关键字高亮、`tbody tr:hover` 三列联动。

汇报结构：

1. 任务信息（编号、commit、日期、状态）
2. 这次做了什么（一段话，说人话）
3. 产出文件（表格：路径 / 行数 / 作用）
4. 关键设计（3–5 条取舍，指向逐行对照文档）
5. 验证结果（命令 + 实际输出）
6. 遗留问题
7. 下一个任务

逐行对照结构：

1. 对照范围（哪些文件、哪些行；哪些不覆盖及理由）
2. 按文件分节，每节一张表：`行号 / 代码 / 说明`
3. 覆盖度自检（总行数 vs 已对照行数）
4. 分组说明的部分要写清分组规则

**汇报不重复逐行内容**，只给结论与索引。

## 4.5 每个任务结束必须同步的两处状态

| 位置 | 更新什么 |
|---|---|
| `reports/开发进度.md` | 任务行标记 ✅、填写提交号与汇报链接 |
| `README.md` | 模块状态表的该模块进度（如 `🟡 进行中 4/7`）；模块收尾改 `✅ 完成（v0.x-mxx）` |
| `docs/tasks/Mxx-任务清单.md` | 任务行标记 ✅ 并链接汇报 |

> 历史问题：M01、M02-01～03 期间只更新了 `开发进度.md`，README 一直停在 M0；从 M02-05 起三处一起改，提交时自查。

## 5. "逐行对照"到底逐到什么程度

逐行对照文档必须覆盖**本任务新增或修改的每一行**。不同类型的产物：

| 产物 | 要求 |
|---|---|
| Java 核心逻辑（Service、状态机、事务方法、校验） | **逐行**：行号 / 代码 / 为什么这么写 |
| 自定义 SQL（扣库存、行锁、版本更新、分页查询） | **逐行**：语句 / 作用 / 为什么不用另一种写法 |
| 实体、DTO、Mapper 接口 | 逐字段/逐方法说明 |
| 建表 DDL | 逐列说明约束来源（与课程 SQL 对齐） |
| 大批量 INSERT 种子数据 | 逐行说明列清单与一行样例；其余按**语句块 + 规则**分组，并写明分组规则 |
| 配置、pom、脚本 | 逐行或按配置项说明 |

判定标准：**读者能不能据此判断"这行代码非写不可"**。
### 5.1 说明必须写"为什么"，禁止复述代码

反例（等于没写）：

```
private Long parseCategoryId(String raw) {   →   "方法 parseCategoryId"
```

正例：

```
if (value <= 0) {                            →   "0 与负数不是合法分类 id"
sort = FEATURED_SORT.get(sku, 100)           →   "默认 100：精选按升序取前 4，默认值必须大于 4"
```

规则：

1. 说明回答**为什么这么写 / 有什么约束 / 放弃了什么**，不复述标识符与签名；
2. 方法/字段先写 javadoc，说明直接取自 javadoc；没有 javadoc 就不生成；
3. 测试夹具用参数值说明（"准备商品 S-3：¥28.00，库存 10，ON_SALE，排序 3"）；
4. **结构性代码不写说明**：import、注解、括号、无 javadoc 的字段/方法、纯标签行，一律渲染为「—」；
5. **禁止分类标签**："导入""注解""字段 X""容器开始""注释续行""属于 X 的一步"这类把代码翻译一遍的文字，一律不要；
6. 说明密度不设指标：宁可有 80% 的「—」，也不要有 80% 的废话。

### 5.2 代码注释规范（M05 起定稿，2026-11-16）

> 从 M05-01 起，新写的代码按这一节执行；M01～M04 已验收代码不回头重写。

**格式**

| 位置 | 要求 | 示例 |
|---|---|---|
| package | 行尾 `//` 一句话说明本文件职责 | `package ...; // 结算确认：把确认页看到的内容固化成快照并复核。` |
| import | **每一条**都有行尾 `//`，说明"为什么需要它" | `import java.io.Serializable; // 快照要放进 Session，必须可序列化。` |
| 类 | 上方 3 行 `//`：依据哪份文档 / 负责什么 / **明确不做什么** | `// M05-01：依据 docs/01 FR-O-01。` |
| 字段 | 行尾 `//`：取值、约束、为什么存 | `private final long cartVersion; // 改数量会 +1，用来发现旧页面。` |
| 方法 | 上方一句话 `/** ... */` | `/** 提交前复核：逐项一致才返回 true。 */` |
| 语句 | **每条**行尾 `//`，写"为什么/约束/取值" | `if (summary.isEmpty()) { // 空车没有可确认的内容。` |
| 测试 | 准备 / 动作 / 每条断言各自一行注释 | `// 另一个标签页把数量 2 改成 3，版本 +1。` |

**量**

- 行尾注释覆盖约 **25%–35%** 的非空行；空行、单独的 `}`、纯注解行不算。
- 不追求 100%：没有"为什么"可写的行（如 `return;` 的收尾）可以不写，但**每条语句至少要能回答"这行为什么存在"**。
- 注释必须回答**为什么/约束/取值**，仍然禁止复述代码（"赋值给 x""调用方法"一律不要）。

**与旧规则的关系**

- 5.1 的"import、字段、结构性代码一律渲染为「—」"只适用于 M01～M04 已验收代码与它们的逐行验收页；
- M05 起新代码按本节写，逐行验收页的右列直接取行尾注释，因此"说明"与"源码注释"是同一句话，不再靠生成器补。

## 6. 模块收尾

一个模块的所有任务完成后：

1. 写模块总汇报 `reports/Mxx-<模块名>.md`：目标、架构位置、任务清单完成情况、验收对照、遗留问题、下一步。
2. 打 tag：`v0.<n>-m<xx>`。
3. 更新 `reports/README.md` 的进度表。

模块总汇报 **不重复**各增量汇报的逐行内容，只做汇总与交叉引用。

---

## 7. 每个任务的完成定义（DoD）

- [ ] 验收命令实际执行过，输出写进汇报
- [ ] 新增/修改的代码有对应测试，或说明为何不需要
- [ ] 汇报已写，行号与本次提交一致
- [ ] 任务清单已勾选
- [ ] 已 commit 并 push

任一条不满足，任务视为未完成，不进入下一个任务。

---

## 8. 与 GitHub 的关系

- **模块分支开发**：每个模块开 `feat/mxx-*`，任务 commit 进分支并**当天推送**，`main` 始终保持可运行。
- **通过测试才合并**：模块全部任务完成、`mvn verify` 全绿、模块总汇报写完，才合并回 `main` 并打 tag。
- 单人项目不强制 PR，但合并前必须自己跑一遍模块测试。
- 任务清单与汇报都在仓库里，汇报时按 `reports/` 目录就能讲清开发过程。
- 不补造提交历史；合并用 `--no-ff` 保留模块边界。
