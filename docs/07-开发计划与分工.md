# 07 · 开发计划与分工

> 组队情况：**1 人独立完成**（指导书允许 1–3 人）。
> 本计划按 5 周排，周次是相对值，请按实际截止日期平移（当前基线：2026-11-14 起）。

---

## 1. 总体节奏

```
W1  工程骨架 + 数据 + 商品浏览（首页/列表/详情）
W2  登录会话 + 权限 + 购物车
W3  结算 + 下单事务 + 订单查询 + 取消
W4  模拟支付 + 状态机 + 管理端（分类/商品/补货/查单/发货）
W5  P1（资料/改密/收货/用户/相册）+ 并发与事务验证 + 文档与实验报告
```

每周固定动作：周一排本周 AC → 周末跑一遍已完成的 AC 并记录证据。**不做"最后一周补测试"。**

---

## 2. 六阶段与退出检查

| 阶段 | 主要产物 | 退出检查 |
|---|---|---|
| 1 工程初始化 | 清理包名、补依赖、数据源、最小 MVC、分页、错误页、测试、Git | 一次真实请求能打通 Controller→Service→Mapper→MySQL→Thymeleaf，测试可跑 |
| 2 商品模块 | 首页、列表、详情、搜索、排序、分页 | 浏览/筛选/详情/边界（下架、售罄、无相册）通过 |
| 3 用户模块 | 登录、Session、退出、拦截器、CSRF | 正确/错误/禁用/角色不符/越权全部通过 |
| 4 购物车模块 | 加车、改量、移除、徽标、失效条目 | 合并、版本、数量上限、种类上限、持久化、归属通过 |
| 5 订单模块 | 结算确认、原子下单、订单列表/详情、取消恢复 | 多明细、快照、失败回滚、取消幂等通过 |
| 6 支付模块 | 模拟成功/失败、重复支付、支付与取消竞争 | 状态机、库存不重复扣、两端联动通过 |

管理端与阶段 2/5/6 并行推进：分类与商品维护在阶段 4 前完成，查单与发货在阶段 6 前完成。

## 5. 单人开发的时间分配建议

| 类型 | 占比 | 说明 |
|---|---|---|
| 业务代码 | 55% | Service 是重点，模板少花时间 |
| 页面与样式 | 20% | 直接复用 `demo/` 的 CSS 与结构 |
| 数据与 SQL | 10% | 一次写对，避免反复重灌 |
| 测试与验证 | 15% | 每完成一个 AC 就记录，不后补 |

单人最容易翻车的地方：**先做页面后做事务**。正确顺序是"Service 测试通过 → 再套模板"。

## 6. 砍功能线（时间不够时按序放弃）

1. 管理端相册维护（P1 最后一项）
2. 管理端用户启停（P1）
3. 个人资料（保留修改密码）
4. 确认收货（保留 `COMPLETED` 的种子数据展示）

**绝不能砍**：下单事务、取消恢复、支付幂等、归属校验、CSRF、补货并发。

## 7. 风险登记

| 风险 | 概率 | 影响 | 应对 |
|---|---|---|---|
| JDK 27 / Boot 4 与机房环境不一致 | 中 | 高 | 提交前在目标 JDK 上完整构建；保留降级到 Boot 3.5 的方案（见 02 §9.1） |
| 种子数据重写耗时超预期 | 中 | 中 | 先写 10 个商品跑通流程，再批量生成到 60 |
| 图片素材缺失 | 高 | 低 | 统一用 SVG 生成封面与相册，不依赖外部图片 |
| 事务/锁写错导致死锁 | 中 | 高 | 严格按"用户 → 车 → 商品 ID 升序 → 订单"顺序加锁 |
| P1 全做导致 P0 延期 | 中 | 高 | 严格执行 §6 砍功能线 |
| 单人时间不足 | 中 | 高 | 每周检查 AC 完成率，低于计划立即砍 P1 |
| 文档与代码不一致 | 中 | 中 | 改动规则时同步改 01/03/04，评审时对表 |

## 8. Git 规范

```
main                 # 可运行、可验收
feat/<模块>          # 如 feat/cart、feat/order
fix/<问题>           # 如 fix/payment-idempotent
```

提交信息：

```
feat(order): 下单事务写入订单与明细并扣减库存
fix(cart): 修复同商品重复加入未累加的问题
docs(db): 补充种子数据规格
test(order): 增加取消订单库存恢复用例
```

要求：

- 每个 AC 至少一次可定位的提交；
- 不提交 `target/`、`.idea/`、本地密码、`.research/`；
- 不补造提交历史（指导书明确要求真实记录）。
