# 02 · 概要设计说明书

---

## 1. 设计原则

1. **业务规则只落在一层**：所有校验、状态迁移、库存与金额计算写在 Service，Controller 只做参数绑定与页面跳转，Mapper 只做 SQL。
2. **数据库是唯一事实来源**：页面不缓存价格，Session 不存购物车，任何展示值都来自本次查询。
3. **两端只共享数据库**：不通过 HTTP 互相调用业务、不共享 Session；业务代码以构建内的共享模块复用，两个应用仍各自独立启动（模块划分见 09 篇）。跨端一致性靠数据库事务与页面重新查询。
4. **失败即整体回滚**：交易类操作一个事务，不做"部分成功"。
5. **诚实展示**：没有实现的能力不放入口。

## 3. 分层与依赖

```
controller  ──▶  service  ──▶  mapper  ──▶  MySQL
     │              │
     │              └──▶  entity / enums / dto
     └──▶  templates（Thymeleaf）
```

- **依赖方向单向**：Controller 依赖 Service，Service 依赖 Mapper；Mapper 不感知 Service。
- **事务边界在 Service**：`@Transactional` 标在 Service 方法上，Controller 不开事务。
- **实体不做业务判断**：`entity` 只映射列，状态判断放 `enums` + Service。
- **视图模型 `dto`**：列表/详情页需要的组合数据（商品 + 分类 + 库存状态）由 Service 组装，不把 Entity 直接丢给模板。

## 5. 关键配置

`application.yaml`（两端共用骨架，值不同）：

```yaml
server:
  port: 8080                      # 管理端 8081
  servlet:
    context-path: /               # 管理端 /admin
    session:
      timeout: 30m
      cookie:
        name: CARTOON_USER_SESSION   # 管理端 CARTOON_ADMIN_SESSION
        http-only: true
        same-site: lax
spring:
  datasource:
    url: jdbc:mysql://localhost:3306/MyCartoonStore?useUnicode=true&characterEncoding=utf-8&serverTimezone=Asia/Shanghai&useSSL=false&allowPublicKeyRetrieval=true
    hikari:
      connection-init-sql: "SET time_zone = '+08:00'"
      maximum-pool-size: 10
  sql:
    init:
      mode: never                 # 启动绝不建表、绝不灌数据
  thymeleaf:
    cache: false                  # 仅 dev
    encoding: UTF-8
```

约定：

- **数据库只主动初始化一次**，应用启动不执行任何 DDL/DML。
- 时间统一按 `Asia/Shanghai` 解释，连接时区与 JVM 时区一致。
- 密码、数据库口令不提交版本库，`application-dev.yaml` 用本地占位。

## 6. 会话、身份与防护

### 6.1 会话内容

Session 只存两样：

1. `SessionUser`：`userId`、`displayName`、`role`、`status`（登录时快照）。
2. `checkoutSnapshot`：结算临时确认（见 §7.3）。

**其余一律现查数据库**：每次受保护请求用 `userId` 重新读 `store_user`，校验 `status = ENABLED` 且 `role` 匹配。这样"已登录后被禁用"也能立即生效。

### 6.2 登录态建立

```
POST /login
  → 校验用户名/密码（BCrypt.matches）
  → 校验 role = CUSTOMER 且 status = ENABLED
  → session.invalidate() 后新建 Session（防会话固定）
  → 写入 SessionUser
  → 302 到 returnUrl（仅站内白名单）或 /main
```

> 实现状态：管理端登录已用 `changeSessionId()` 轮换会话；用户端仍沿用原会话，防会话固定留到 M09 统一处理。

### 6.3 CSRF

不引入 Spring Security 全栈，只做**同步令牌**：

- `CsrfFilter` 在每次请求开始时确保 Session 里有 `csrfToken`（UUID）。
- 所有 `POST/PUT/DELETE` 必须带表单隐藏域 `_csrf`，值与会话一致，否则 403。
- 模板通过 `@ControllerAdvice` 注入 `csrfToken`，统一由 `fragments/csrf.html` 渲染。
- `GET` 不得产生业务副作用；退出、移除、支付、发货、上下架一律 `POST`。

> 实现状态：CSRF 尚未启用，M09 统一加入（届时所有写表单补 `_csrf`，并补 AC-31 的 403 用例）。

### 6.4 密码

- `spring-security-crypto` 的 `BCryptPasswordEncoder(10)`，只引这一个构件，不引 `spring-boot-starter-security`。
- 登录失败不区分"用户不存在 / 密码错 / 被禁用"，统一文案。
- 日志里不打印密码、散列、完整手机号。

### 6.5 错误处理

`GlobalExceptionHandler` + `error/` 模板：

| 情况 | 状态码 | 页面 |
|---|---|---|
| 参数格式/越界/非法枚举 | 400 | `error/400.html`，说明具体参数并可返回 |
| 未登录访问受保护入口 | 302 登录页 | 登录后回原页（不重放写请求） |
| 越权（他人购物车/订单） | 404 | 错误页，不泄露目标对象**是否存在**与任何字段 |
| CSRF 失败 | 403 | 错误页，提示刷新后重试 |
| 商品/分类不存在或已下架 | 404 | `error/404.html` |
| 版本冲突、状态已变化 | 409 | 提示刷新后重试 |
| 技术异常 | 500 | `error/500.html`，不输出 SQL/堆栈 |

## 7. 关键流程

### 7.1 加入购物车

```
POST /cart/items  (productId, quantity)
  ├─ 身份：SessionUser 必须为 CUSTOMER 且 ENABLED
  ├─ 参数：quantity ∈ [1,99]
  ├─ 事务开始
  │   ├─ SELECT ... FROM store_user WHERE id=? FOR UPDATE      -- 同一用户串行
  │   ├─ 查商品：存在 且 status=ON_SALE 且 stock ≥ quantity
  │   ├─ 查购物车：同商品已存在则新数量=旧+quantity，校验 ≤99
  │   ├─ 种类数：新增时校验当前种类 < 20
  │   └─ INSERT / UPDATE cart_item（version+1）
  └─ 事务提交 → 302 回商品页或购物车
```

### 7.2 结算确认（不锁价、不占库存）

```
GET /checkout
  ├─ 读本人全车，关联当前商品名/封面/价格/库存
  ├─ 标记失效条目（DRAFT 或 stock < quantity）
  ├─ 写入 Session.checkoutSnapshot：
  │     [{cartItemId, productId, quantity, cartVersion, price}], totalAmount, userId
  └─ 渲染确认页
```

### 7.3 下单（核心事务）

```
POST /checkout
  ├─ 事务开始
  │   ├─ SELECT store_user ... FOR UPDATE                      -- 先锁人
  │   ├─ 读本人全车（FOR UPDATE 或依赖用户锁串行）
  │   ├─ 比对 checkoutSnapshot：条目集合、数量、价格、版本一致？
  │   │     不一致 → 409「购物车或价格已变化，请重新确认」
  │   ├─ 收集 productId，按 ID 升序 SELECT ... FOR UPDATE      -- 统一顺序防死锁
  │   ├─ 逐条校验：ON_SALE、stock ≥ quantity
  │   ├─ INSERT sales_order（PENDING_PAYMENT, total_amount, 收货快照）
  │   ├─ 批量 INSERT sales_order_item（SKU/名称/封面/单价/数量/行金额 快照）
  │   ├─ UPDATE product SET stock=stock-?, version=version+1 WHERE id=? AND stock>=?
  │   │     影响 0 行 → 抛异常回滚
  │   └─ DELETE cart_item WHERE id IN (本次核对条目) 并校验删除行数
  └─ 提交 → 清 Session 确认 → 302 /orders/{orderNo}
```

### 7.4 模拟支付

```
POST /payment/{orderNo}/success
  ├─ 事务开始
  │   ├─ SELECT sales_order ... FOR UPDATE
  │   ├─ 校验：user_id = 当前用户 且 status = PENDING_PAYMENT
  │   │     已 PAID → 幂等提示，保持首次凭证
  │   │     已 CANCELLED → 409/提示不可支付
  │   ├─ UPDATE status=PAID, payment_method='MOCK',
  │   │          payment_no=服务端生成, paid_at=NOW()
  │   └─ 不触碰 stock
  └─ 提交 → 302 /orders/{orderNo}
```

### 7.5 取消待支付

```
POST /orders/{orderNo}/cancel
  ├─ 事务开始
  │   ├─ SELECT sales_order ... FOR UPDATE
  │   ├─ 校验归属 + status = PENDING_PAYMENT
  │   ├─ UPDATE status=CANCELLED, cancelled_at=NOW()
  │   ├─ 按明细 productId 升序：UPDATE product
  │   │      SET stock=stock+?, version=version+1
  │   └─ 不改商品状态（下架仍下架）
  └─ 提交
```

### 7.6 发货

```
POST /admin/orders/{orderNo}/ship
  ├─ 事务开始
  │   ├─ SELECT sales_order ... FOR UPDATE
  │   ├─ 校验 status = PAID（其余状态拒绝）
  │   └─ UPDATE status=SHIPPED, shipped_at=NOW()（首次时间不再改写）
  └─ 提交
```

## 8. 并发与一致性策略

### 8.1 锁顺序（防死锁）

```
用户行 → 该用户购物车 → 商品行（按 productId 升序） → 订单行
```

- 购物车写操作与下单共享同一个互斥点：**先锁用户行**。
- 支付与取消只锁订单行；取消恢复库存时按商品 ID 升序。
- 后台补货用原子 `UPDATE ... SET stock = stock + ?`，不做"读-改-写"。

### 8.2 版本号

| 表 | 何时 +1 | 用途 |
|---|---|---|
| `product.version` | 资料编辑、价格、上下架、补货、下单扣减、取消恢复 | 后台旧表单保存冲突检测 |
| `cart_item.version` | 数量修改 | 旧页面覆盖检测 |

商品资料编辑：`UPDATE product SET ..., version=version+1 WHERE id=? AND version=?`，影响 0 行 → 409。

### 8.3 事务与异常

- 交易方法 `@Transactional(rollbackFor = Exception.class)`。
- 捕获异常后不得"当作成功提交"；要么抛出让容器回滚，要么在事务外决定重试。
- 业务失败（库存不足、版本冲突）抛 `ApiException`，由全局处理器转成 409/400，事务自动回滚。
- 死锁、超时同样整体回滚，页面提示"操作冲突，请重试"。

### 8.4 金额

- 一律 `BigDecimal`，`scale=2`，`RoundingMode.UNNECESSARY`——超精度输入直接拒绝，不静默舍入。
- 行金额 = 单价 × 数量；订单总额 = Σ 行金额；支付金额 = 订单总额。
- 范围超出 `DECIMAL(12,2)` 或 `INT` 时拒绝并回滚。

### 9.1 版本风险

现有骨架用 **Spring Boot 4.1.2 + JDK 27**，而课程机房可能是 JDK 17/21 + Boot 3.x。风险与对策：

- 若老师环境固定 Boot 3.x：把 parent 降到 3.5.x，`spring-boot-starter-webmvc` 换成 `spring-boot-starter-web`，MyBatis-Plus starter 换成 `mybatis-plus-spring-boot3-starter`。业务代码不受影响。
- **提交前必须在与机房一致的 JDK 上完整构建一次**。
