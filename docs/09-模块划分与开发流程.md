# 09 · 模块划分与开发流程

> 目标：把项目拆成**可独立编译、独立测试、独立评审**的模块；每个模块通过测试门槛后才合并进 `main`；每个模块产出一份开发汇报。

---

## 1. 为什么要拆

| 问题 | 拆分后的解法 |
|---|---|
| 一个人写完全部代码，出错难定位 | 每个模块有自己的测试，红了就是这一块 |
| 业务规则散落在 Controller / 模板里 | 规则只允许写在 service 层，web 层只做参数与渲染 |
| 改支付影响下单 | 模块边界 + 依赖方向，改动面可预测 |
| 无法回答"这部分做完了吗" | 每个模块有 Definition of Done 与验收号 |
| 答辩讲不清设计 | 每模块一份汇报，含逐行代码说明 |

---

## 2. 模块划分

### 2.1 构建结构

```
mycartoonstore/                 (parent pom，packaging=pom，只做依赖管理)
├── cartoon-common/             技术公共件：异常、分页参数、金额、枚举、SessionUser、CSRF
├── cartoon-catalog/            分类、商品、相册（实体 + Mapper + 服务）
├── cartoon-account/            账号、登录校验、密码、资料
├── cartoon-cart/               购物车
├── cartoon-order/              结算确认、订单、取消
├── cartoon-payment/            模拟支付（依赖 order 的状态机）
├── cartoon-user-web/           用户端应用：Controller + Thymeleaf，8080
├── cartoon-admin-web/          管理端应用：Controller + Thymeleaf，8081
└── cartoon-test-support/       测试基座：测试库初始化、构造函数、Mock 工厂
```

### 2.2 各模块职责

| 模块 | 负责 | 不负责 | 依赖 | 测试类型 |
|---|---|---|---|---|
| `common` | 业务异常、错误码、分页与排序参数对象、金额工具、通用枚举、`SessionUser`、CSRF 过滤器 | 任何业务规则 | 无 | 纯单元 |
| `catalog` | 分类树校验、商品查询（首页/列表/详情）、上下架、补货、相册 | 购物车、订单 | common | 单元 + 集成 |
| `account` | 登录校验、BCrypt、账号状态、资料与改密 | 会话存储（在 web 层） | common | 单元 + 集成 |
| `cart` | 加车合并、数量与种类上限、版本、失效判断 | 结算、扣库存 | common, catalog | 单元 + 集成 |
| `order` | 结算快照、原子下单、订单查询、取消恢复 | 支付凭证生成 | common, catalog, cart | 单元 + 集成（事务） |
| `payment` | 支付成功/失败、幂等、凭证生成 | 发货 | common, order | 单元 + 集成（并发） |
| `user-web` | 路由、表单绑定、Session、拦截器、模板 | 业务判断 | 全部业务模块 | MockMvc + 手工 AC |
| `admin-web` | 后台路由、模板 | 业务判断 | 全部业务模块 | MockMvc + 手工 AC |
| `test-support` | 测试 schema 初始化、测试账号、断言工具 | 业务代码 | common | 自身不测 |

### 2.3 依赖规则（违反即评审不通过）

1. **单向**：`web → 业务模块 → common`，禁止反向与循环。
2. **业务模块之间**：只允许 `order → cart/catalog`、`payment → order`，其余互不依赖。
3. **Mapper 只被本模块的 Service 使用**，跨模块拿数据必须走对方 Service。
4. **web 层不得出现**：SQL、金额计算、状态迁移判断、库存加减。
5. **common 不得依赖** Spring Web / MyBatis / Thymeleaf 之外的任何业务包。

> 用 Maven 的 `maven-enforcer-plugin` 加 `banned-dependencies` 规则，CI 里自动检查反向依赖。

## 3. 开发流程（每个模块一遍）

> 模块内部还要再拆任务，逐个任务提交与汇报，见 [10-任务清单与增量汇报规范](10-任务清单与增量汇报规范.md)。

```
① 建分支   git switch -c feat/m03-cart
② 写测试   先写 Service 单元测试（红灯）
③ 写实现   最小实现让测试转绿
④ 集成测   真实 MySQL，验证事务/约束
⑤ 写汇报   reports/M03-购物车.md（模板见 docs/templates/）
⑥ 自检     mvn -pl <模块> -am verify 全绿 + 依赖规则通过
⑦ 合并     PR/本地合并到 main，打 tag v0.3-m03
⑧ 记录     README 的模块进度表打勾
```

**门槛（Definition of Done）**

- [ ] `mvn -pl <module> -am verify` 通过，0 失败 0 跳过（有意跳过需注明）
- [ ] 新增/修改的每个业务分支都有对应用例
- [ ] 涉及数据库的模块，集成测试在真实 MySQL 上跑过
- [ ] 依赖方向检查通过（enforcer）
- [ ] `reports/Mxx-*.md` 已写，含逐行对照
- [ ] 对应 AC 手工验证并记录证据
- [ ] 无 `TODO`、无注释掉的死代码、无 `System.out`

不满足任一条 → 不合并。

## 4. 模块顺序与里程碑

| 编号 | 模块 | 主要产出 | 对应 AC |
|---|---|---|---|
| M00 | 工程基座 | parent pom、common、测试基座、CI 脚本、Git 规范 | — |
| M01 | 数据库与实体 | 两份 SQL 改写、七表实体、Mapper、种子数据 | AC-32 |
| M02 | 商品浏览 | `catalog` + 用户端首页/列表/详情 | AC-01~04 |
| M03 | 账号与权限 | `account` + 登录/退出/拦截器/CSRF | AC-05~07 |
| M04 | 购物车 | `cart` + 购物车页 | AC-08~11 |
| M05 | 订单 | `order` + 结算页/下单事务/订单页/取消 | AC-12~17、19、21~23 |
| M06 | 支付 | `payment` + 支付页 + 支付/取消竞争 | AC-20、24 |
| M07 | 管理端 | `admin-web` + 分类/商品/补货/查单/发货 | AC-25~29 |
| M08 | P1 扩展 | 资料改密、确认收货、用户启停、相册 | AC-33、34 |
| M09 | 验收交付 | 全量回归、证据、README、答辩材料 | AC-30、31 |

每个 M 对应一个分支、一份汇报、一个 tag。

## 5. 测试策略

| 层 | 工具 | 范围 | 是否连库 |
|---|---|---|---|
| 单元 | JUnit 5 + Mockito | Service 分支、金额、状态迁移、分页参数 | 否 |
| 集成 | Spring Boot Test + 真实 MySQL（`MyCartoonStore_test`） | Mapper SQL、事务回滚、唯一约束、乐观锁 | 是 |
| Web | MockMvc | 路由、参数校验、状态码、重定向、越权 | 是（测试库） |
| 手工 | Chrome/Edge | 两端联调、并发、UI 状态 | 是（演示库） |

- 测试库脚本：`cartoon-test-support/src/main/resources/sql/test-schema.sql`，每个测试类前重建。
- 事务测试必须从**真实业务入口**触发，不能在测试方法上包一层 `@Transactional` 掩盖边界。
- 并发测试用 `ExecutorService` + `CountDownLatch`，两个独立连接。

## 6. 汇报规范

每个模块完成后写 `reports/Mxx-<模块名>.md`，固定 9 节：

| 节 | 内容 | 常见不合格 |
|---|---|---|
| 1 模块信息 | 编号、分支、提交号、日期、作者 | 缺提交号 |
| 2 这一部分是做什么的 | 业务目标、边界、**明确不做什么** | 抄 PRD 原文 |
| 3 设计与取舍 | 3–5 个关键决策 + 为什么 + 放弃了什么方案 | 只写"用了 MyBatis-Plus" |
| 4 文件清单 | 新增/修改文件表（路径 + 行数 + 作用） | 贴整棵树 |
| 5 代码逐行对照 | 核心类逐行表 | 贴整段代码不解释 |
| 6 测试 | 用例表、命令、结果、覆盖率 | 只写"测试通过" |
| 7 验收对照 | AC 编号与证据位置 | 不写证据 |
| 8 问题与风险 | 已知缺陷、待确认项 | 写"无" |
| 9 下一步 | 下一个模块的前置条件 | 写"继续开发" |

### 6.1 "代码逐行对照"怎么做

对每个**核心类**（Service、状态机、事务方法），给一张表：

| 行 | 代码 | 说明 |
|---|---|---|
| 42 | `if (order.getStatus() != PENDING_PAYMENT)` | 只有待支付可取消，其余状态直接拒绝 |
| 43 | `throw new BizException(CONFLICT, "订单状态不支持取消");` | 转 409，事务回滚 |

约定：

- 只对**手写核心代码**逐行；Lombok 生成、getter/setter、import、Mapper 接口不逐行。
- 一次汇报逐行 2–4 个类，不超过 200 行；其余类给"职责 + 关键分支"摘要。
- 行号以提交时的文件为准。

## 7. Git 规范

| 项 | 规则 |
|---|---|
| 分支 | `main` 保持可运行；`feat/mxx-name` 开发；`fix/...` 修缺陷 |
| 合并 | 模块分支测试全绿后合并，合并提交带模块号 |
| 提交 | `feat(cart): 加入购物车时校验累加后数量上限` |
| 标签 | `v0.2-m02`、`v0.3-m03`，与模块一一对应 |
| 禁止 | 提交 `target/`、`.idea/`、`.research/`、本地密码；禁止补造历史 |

## 8. 与课程交付的关系

- 交付物仍是**两个可独立启动的应用**：`cartoon-user-web`（8080）与 `cartoon-admin-web`（8081），各自有 `application.yaml` 和 `spring-boot-maven-plugin`。
- 多模块只是**构建期组织方式**，两个应用可分别 `mvn -pl cartoon-user-web spring-boot:run` 启动，不依赖对方。
- 与 PRD 的差异记入 08 篇：由"两个独立工程、不共享 JAR"调整为"单仓库多模块、两个独立应用、共享业务库模块"。理由：单人开发下避免同一套业务规则写两遍，且模块化本身便于独立测试。
