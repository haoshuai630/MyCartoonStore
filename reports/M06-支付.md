## 1. 模块目标与范围

**目标**：让待支付订单可以完成"教学模拟支付"——成功则转到 PAID 并保留凭证与时间，
失败则保持待支付可重试；整个过程中库存不再变动，支付与取消并发时只有一种迁移成功。

**范围内**：
- 支付服务：订单行锁、归属 404、已支付幂等、已取消/已发货 409、凭证生成与查重
- 支付页：大字金额、教学声明、两个 POST 按钮、返回详情/取消入口
- 入口：详情页与列表卡片的「去支付」，卡片与详情、支付页三处取消二次确认
- 保护：`/payment/**` 纳入登录拦截
- 验收：AC-20 六个场景 + AC-24 并发

**明确不做**：
- 真实支付渠道、回调、对账、退款
- 发货与确认收货（M07 / M08-P1）
- CSRF token（M09 统一加）
- 支付页商品明细（审阅确认不展示）

## 4. 架构位置与关键设计

```
user-web  PaymentController（支付页 / 成功 / 失败）
              │
              ▼
cartoon-payment  PaymentService ── PaymentNoGenerator
              │                        │
              ▼                        ▼
      cartoon-order            SalesOrderMapper
   （SalesOrder / Mapper）   （lockByOrderNo / countByPaymentNo）
```

1. **先锁行再判状态**：`paySuccess` / `payFailure` 都先 `SELECT ... FOR UPDATE` 锁订单行，
   并发的支付与取消在这一个互斥点上排队；第二个事务看到的是已提交后的状态。
2. **幂等不覆盖**：看到 `PAID` 直接返回 `ALREADY_PAID`，不重新生成凭证、不改 `paid_at`；
   第二次成功与第一次的凭证、时间完全一致。
3. **支付不碰库存**：模块不注入商品 Mapper，集成用例同时断言库存、版本、购物车三处不变。
4. **失败是"不写库"的分支**：数据库没有 `PAY_FAILED` 状态，失败后仍是 `PENDING_PAYMENT`，
   三件套保持为空；回支付页用 flash 提示"支付失败，可重试"。
5. **页面诚实**：支付页只展示订单总额与教学声明，不出现支付宝/微信/银行卡图标；
   入口只在待支付出现，取消统一二次确认。
