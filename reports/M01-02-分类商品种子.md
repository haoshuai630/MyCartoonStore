## 3. 逐行分析

### 3.1 为什么用生成器，而不是直接手写 SQL

- **做法**：Python 脚本生成 SQL，产物提交进仓库。
- **为什么**：60 个商品的 SKU、分类 id、库存、状态、上架时间都有强规则；手写时"少写一个 DRAFT""库存边界漏一个"很难发现，而脚本可以断言数量。
- **放弃的方案**：直接手写 60 行 `INSERT`。短期快，但 M01-03 还要加 100 条相册、M01-04 加 20 条明细，手写会失控。
- **代价**：多一个 Python 文件。已在 `db/README.md` 与文件头注明"产物是纯 SQL，脚本仅用于维护"，不要求环境装 Python。

### 3.2 `build_products()`（第 111–145 行）

| 行 | 代码 | 说明 |
|---|---|---|
| 111 | `def build_products():` | 唯一入口，返回 60 条 dict，与 SQL 无关，便于 M01-03/04 复用 |
| 113 | `for idx, ip in enumerate(IPS):` | 外层按作品循环，保证每部作品的 12 件连续排列，id 稳定 |
| 114 | `comic_id = 100 + idx * 2` | 二级分类 id 从 100 起，单行本用偶数号：100/102/…/108 |
| 115 | `merch_id = 101 + idx * 2` | 官方周边用奇数号：101/103/…/109。与 `category` 种子里的 id 一一对应 |
| 116 | `for n in range(1, 7):` | 每部作品 6 卷 |
| 117 | `sku = f"{ip['code']}-C{n:02d}"` | SKU 规则 `{IP}-C01..C06`；两位补零，保证字符串排序与卷次一致 |
| 118 | `status = "DRAFT" if n == 6 else "ON_SALE"` | **只有第 6 卷下架**，5 部共 5 件 |
| 122 | `name = f"《{ip['cn']}》第{n}卷"` | 书名带书名号，列表与订单快照都用它 |
| 126 | `"stock": 0 if status == "DRAFT" else VOLUME_STOCK.get(sku, 11 + n)` | 下架商品库存 0；上架默认 12–17，`STARLINE-C02` / `MISTPORT-C03` 由覆盖表指定为 1 / 0 |
| 128 | `"sort": FEATURED_SORT.get(sku, 100)` | **默认 100 而不是 0**，见 §3.4 的踩坑记录 |
| 129 | `"age": NEWEST_AGE.get(sku, 5 + idx * 6 + n)` | 距今天数；三个指定 SKU 取 0/1/2，保证"新品上架"三条确定 |
| 131 | `for j, (name, price, stock, status) in enumerate(MERCH[ip["code"]], start=1):` | 周边数据表里直接带库存与状态，避免再写分支 |
| 132 | `sku = f"{ip['code']}-M{j:02d}"` | 周边 SKU `{IP}-M01..M06` |
| 142 | `"sort": FEATURED_SORT.get(sku, 100)` | 周边与单行本共用精选排序 |

**关键约束**：商品只能挂二级分类——这里 `cat` 取的是 100–109，绝不可能是一级（1–5）。数据库外键不拦这个，靠的是生成器不产生这种数据 + M02 的 Service 校验。

### 3.3 分类 id 规划（第 103、224–250 行）

| 行 | 代码 | 说明 |
|---|---|---|
| 103 | `CATEGORY_IDS = {ip["code"]: (i + 1) * 1 for i, ip in enumerate(IPS)}` | 一级 id 固定 1–5，与作品顺序绑定 |
| 231 | `INSERT INTO category (id, code, parent_id, name, sort_order) VALUES` | 一级 5 行，`parent_id = NULL` |
| 238 | `INSERT INTO category (...) VALUES` | 二级 10 行，`parent_id` 指向上表 id |

**为什么用固定 id**：商品要引用分类。若依赖自增，商品 INSERT 就得写子查询，SQL 可读性差且容易错位。固定 1–5 / 100–109 后，商品行里的 `category_id` 直接可读。

### 3.4 过程中撞到的两个坑（真实记录）

**坑 1：下架商品变成 10 件**

第一版把"每部作品的第 6 件周边"都设成 `DRAFT`，结果：

```
DRAFT 10 / ON_SALE 50   ← 期望 6 / 54
```

原因：5 部作品 × （第 6 卷 + 第 6 件周边）= 10。修正为只有 `STARLINE` 的「全彩设定画集」下架，其余 4 件周边恢复上架。

**坑 2：`sort_order` 语义写反**

第一版默认 `sort_order = 0`，只给 4 个精选商品设 1–4。但 PRD 规定精选按 `sort_order ASC` 取前 4——**0 排在 1 前面**，结果精选出来的是 `STARLINE-C02/C03/C04/C05`（全 0），指定的 4 个反而排到最后。

修正：默认值改为 `100`，精选商品保留 1–4：

| SKU | sort_order |
|---|---|
| STARLINE-C01 | 1 |
| MISTPORT-C01 | 2 |
| IRONWOOD-M01 | 3 |
| CICADA-C05 | 4 |
| 其余 56 件 | 100 |

这两个坑都是**验证查出来的**，不是看代码看出来的——说明"跑一遍 + 对数字"比"仔细检查"有效。

### 3.5 SQL 语句块（第 224–296 行）

| 行 | 语句块 | 说明 |
|---|---|---|
| 224 | `INSERT INTO store_user ...` | 4 行，密码为 BCrypt 散列（见 §4.4 验证），`carol` 状态 `DISABLED` |
| 231 | 一级分类 5 行 | `code` 用作品英文名，`sort_order` 1–5 决定首页顺序 |

### 4.6 中文写入完整性

```
SELECT CHAR_LENGTH(name), HEX(LEFT(name,1)) FROM product WHERE sku='STARLINE-C01';
```
