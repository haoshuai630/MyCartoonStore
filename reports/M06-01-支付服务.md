## 2. 这次做了什么

给 `cartoon-payment` 补上第一个真实功能：**把一笔待支付订单安全地变成已支付**。

- `PaymentService.paySuccess`：锁订单行 → 归属校验（他人/不存在 404）→ 已支付幂等 → 非待支付 409 →
  同一 `UPDATE` 写 `status=PAID / payment_method=MOCK / payment_no / paid_at`，全程不碰库存、明细与购物车。
- `PaymentService.payFailure`：同样先锁行与校验，待支付返回 `FAILED` 且**不写库**；已支付返回 `ALREADY_PAID`；
  已取消 409。
- `PaymentNoGenerator`：`PAY + 时间戳 + 4 位随机`，生成前 `countByPaymentNo` 查重、最多 3 次，失败给 500 可重试文案。
- `PaymentResult`：`PAID / ALREADY_PAID / FAILED` 三态，页面据此决定提示与跳转（M06-02 使用）。

**没有做的**：支付页、路由与入口（M06-02）；库存/购物车不变的集成断言与 AC-24 并发用例（M06-03）。

## 3. 三个设计点

### 3.1 先锁行，再判状态：幂等与 409 都建立在同一个互斥点上

`paySuccess` 的第一行就是 `lockByOrderNo`（`SELECT ... FOR UPDATE`），拿到锁之后才看 `status`。
并发的两次支付、以及支付与取消之间，都在这一个订单行上排队：第二个事务看到的必然是第一个提交后的状态，
于是"已支付 → 幂等"和"已取消 → 409"都只可能命中一个分支。`payFailure` 虽然是只读语义，也照样拿行锁，
否则可能读到"取消事务已改状态但未提交"的中间态，给出与最终结果矛盾的提示。

### 3.2 幂等分支不生成、不覆盖

`PAID` 分支直接 `return ALREADY_PAID`，既不调 `PaymentNoGenerator`，也不执行 `updateById`。
测试用 `verify(never()).updateById(...)` 与 `verifyNoInteractions(paymentNoGenerator)` 把这个约定钉死——
"再次成功"不能变成"换一个新凭证"，否则对账时同一单会出现两个凭证号。

### 3.3 失败是"不写库"的分支，而不是"写一个失败状态"

数据库的 `status` 只有五种，没有 `PAY_FAILED`；FR-P-01 的要求也是失败后仍为 `PENDING_PAYMENT`。
所以 `payFailure` 只做校验与返回，不产生任何 `UPDATE`。凭证与支付时间因此在失败后仍为空，
M06-03 的集成用例会直接对三列断言为空。
