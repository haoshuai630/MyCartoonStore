## 1. 这次做了什么

AC-32 要求「空库执行初始化脚本，同时启动两端」，证明交付物在新机器上可复现。做法是五步：

1. `mysqldump` 备份演示库（保留手工验收留下的账号与订单）；
2. 直接执行仓库里的 `db/02-schema-with-demo.sql`——脚本自己 `DROP DATABASE` 再建，**不额外手工清库**；
3. 核对七张表与种子行数：4 / 60 / 95 / 160 / 10 / 10 / 20；
4. 用这份新库把两端都启动（18080 / 18081），探活与首页都 200；
5. 用备份恢复演示库，行数回到备份前。

全程输出落在 `reports/evidence/m09-ac32-*.txt`，脚本可重复执行。

## 4. 关键设计

### 4.1 执行交付脚本原文，不改库名

`02-schema-with-demo.sql` 头部就写着 `DROP DATABASE IF EXISTS MyCartoonStore; CREATE DATABASE …`，
所以"空库"这一步不需要单独手工 DROP——直接跑脚本就是最真实的复现路径。若为了避开演示库而临时改库名，
证据强度会下降（跑的不是交付物），因此选择备份 + 恢复。

### 4.2 备份先做，恢复放最后

演示库里已经有手工验收产生的账号与订单（6 用户 / 15 订单）。直接重建会丢这些数据，所以第一步 `mysqldump` 到
`_scratch/`（不提交，避免把数据快照塞进仓库），第五步再导回；恢复后的行数与备份前完全一致。

### 4.3 临时端口，不动正在运行的实例

8080 / 8081 上跑着旧构建，AC-32 用 18080 / 18081 另起两个进程。这样既不影响日常使用，也顺带证明了
"两端可独立启动"——`cartoon-user-web` 与 `cartoon-admin-web` 各自 `java -jar` 都能起来。

### 4.4 行数用一条 UNION 查询核对

七张表一次查完，输出固定格式，方便脚本逐项比对并在不一致时报 MISMATCH。`--baseline` 开关决定是否按种子口径判定：
恢复后行数会大于种子（有手工数据），此时只要求"能查出来"，不要求等于 4/60/95/…

### 4.5 证据按步骤分文件

最初所有输出写进同一个 `m09-ac32-empty-db.txt`，后一步会覆盖前一步。改成 `1-backup` / `2-init` / `3-verify` /
`4-apps` / `5-restore` 五个文件，谁覆盖谁一眼能看出来。
