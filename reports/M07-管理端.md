## 1. 模块目标与范围

**目标**：让管理员能在 `:8081/admin` 独立登录，维护两级分类与商品（含上下架、增量补货），
查询全站订单并对 `PAID` 订单发货；用户端立刻看到同一份数据库的变化。

**范围内**：

- 身份：用户端/管理端登录互斥、失败统一文案、受保护请求每请求重读账号（M07-01/02）
- 分类：两级树、新增一级/二级、编辑名称与排序、删除前引用校验（M07-03/04）
- 商品：列表筛选、新增（默认 DRAFT）、编辑（版本冲突 409）、上下架、增量补货（M07-05/06/07）
- 订单：全站列表、详情（快照/收货/凭证/所属用户）、发货（仅 PAID、幂等）（M07-08）
- 骨架：管理端登录页、控制台、8 个页面、`admin.css`、错误页、管理端测试基座
- 分类页交互（M07-10 追加）：按作品折叠 + 作品名/编码搜索 + 两种空状态

**明确不做**：

- P1 用户启停、相册维护（M08）
- 确认收货（M08）
- CSRF（M09）
- 后台改金额/明细/凭证/状态、删除商品、物流与运单号、统计报表
- 真实图片上传（封面只填站内路径）

## 4. 架构位置与关键设计

```
admin-web  AdminAuthInterceptor / Admin*Controller + Thymeleaf
              │
              ▼
catalog: CategoryAdminService / ProductAdminService
order:   OrderAdminService / ShipService
account: AccountService（登录与批量取名）
```

1. **门禁独立于业务**：`AdminAuthInterceptor` 只回答"能不能进后台"，分类层级、商品版本、订单状态都不是它的事；
   全站拦截 + 白名单，新加页面默认受保护。
2. **业务规则只在 Service**：8 个页面里没有一处层级/版本/状态判断；模板只做 `th:if` 与展示。
3. **版本与行锁两种并发手段各管一段**：商品资料/上下架用 `version` 条件更新；订单发货用 `SELECT ... FOR UPDATE`；
   补货与下单用原子 `UPDATE`（`stock = stock ± n`），互不覆盖。
4. **两个入口互斥、失败同文案**：`authenticateCustomer` / `authenticateAdmin` 共用私有校验，四类失败同为 401 同文案。
5. **诚实展示**：控制台没有统计数字；未接入的入口先显示"待接入"，接入后才变成链接；详情页金额与凭证只读。
