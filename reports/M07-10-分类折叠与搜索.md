## 1. 需求与对应

| 来源 | 要求 | 落实 |

| 需求方（2026-11-17） | 分类维护里每个作品可以展开/收起它的品类 | 每个作品一个 `<details>` 分组，默认收起，点标题行展开 |
| 需求方 | 作品多了不好找，需要搜索作品 | 筛选条加「搜索作品」：名称或编码包含匹配，大小写不敏感 |

**没有做的**：品类名搜索（只搜作品名与编码，避免"搜品类却返回整部作品"的歧义）、分页（搜索已解决定位问题）、拖拽排序。

## 2. 这次做了什么

- `CategoryAdminService.groups(keyword)`：把原来的扁平行改成"作品 + 品类"分组，按作品名或编码过滤；关键字去空白、空不筛选、超长 400。
- 新增 `CategoryGroup`（作品行 + 品类行 + `childCount`）。
- 控制器列表接收 `keyword`，并给页面算好「共 N 部作品 / M 个品类」。
- 模板改为 `<details>` 分组：默认收起；搜索时加 `searched` 标记并默认 `open`；作品行右侧仍是编辑/新增品类/删除；品类表在展开区。
- 空状态区分「还没有作品」与「没有匹配的作品」，后者给「清空搜索」。

## 3. 关键设计

### 3.1 折叠用浏览器原生 `<details>`，不引前端框架

项目约定不写前端框架（docs/01 §1.3），`<details>/<summary>` 零 JS 就能展开收起，
模板里只需 `th:open` 控制搜索时默认展开；`summary` 里的链接与表单加 `stopPropagation`，避免点"编辑"时顺带切换折叠。

### 3.2 搜索在内存里做包含匹配，不走 LIKE

分类总数是几十条，一次查询已经全部取回；在 Java 里做 `contains` 比拼 `LIKE` 更安全——
用户输入 `%`、`_` 不会被当通配符，也不需要额外转义。若将来分类上千，再下推到 SQL。

### 3.3 只筛作品，不筛品类

需求是"作品多了不好找"。若连品类名一起匹配，搜"单行本"会返回所有作品，反而更乱。
搜索框的提示文案写明"作品名或编码"。
