## 3. 逐行分析

### 3.1 头部注释（第 1–7 行）

| 行 | 代码 | 说明 |
|---|---|---|
| 1 | `-- MyCartoonStore 实验一：仅表结构（不含业务数据）` | 标题改成项目名，保留"仅表结构"这个关键信息，避免有人拿它当完整初始化脚本 |
| 2 | `-- 七张表的结构、字段、约束、索引沿用课程 MyPetStore 基线，仅库名与注释本地化。` | **新增**。这是本次任务的全部范围声明，防止后来者以为表结构被改过 |
| 3 | `-- 适用：MySQL 8.0.16+ / 8.4，InnoDB，utf8mb4。` | 原样保留。本机实测 8.4.9 可执行 |
| 4 | `-- 与 02-schema-with-demo.sql 二选一，不按编号依次执行。` | 原样保留，仅补空格。这条最容易被人忽略，两个脚本都含 `CREATE TABLE` |
| 5 | `-- 在空的 MyCartoonStore 库中首次执行；不 DROP、不清空、不覆盖已有表。` | 只换库名。"不 DROP"是安全底线：脚本绝不删数据 |
| 6 | `-- 已有同名表时会报错，请检查目标数据库，不要使用 mysql --force 跳过错误。` | 原样保留。`--force` 会让半套表建出来，比报错更难排查 |
| 7 | `-- 本文件不创建数据库账号，不配置应用密码……` | 原样保留。说明脚本与应用配置的边界 |

**为什么只改注释不改 DDL**：`03-数据库设计说明书` 已声明七表结构是验收基准；改列名或约束会让 `01` 与课程材料、与 `02`、与实体类三处同时漂移。本次改动的价值在于"让人知道这是同一套结构"。

### 3.2 库名（第 12–14 行）

| 行 | 代码 | 说明 |
|---|---|---|
| 12 | `CREATE DATABASE IF NOT EXISTS MyCartoonStore` | `IF NOT EXISTS` 保留：重复执行不会因为库已存在而中断（但表会） |
| 13 | `    CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;` | 原样。排序规则必须与连接串、`SET NAMES` 一致，否则中文比较与唯一键行为会变 |
| 14 | `USE MyCartoonStore;` | 后续所有 DDL 落在该库，避免误建到别的库 |

**为什么不用 `utf8mb4_general_ci`**：课程 CHECK 里用了 `CHAR_LENGTH(TRIM(...))` 与大小写敏感/不敏感的混合语义（`ascii_bin` 列），换排序规则会让 `uk_category_sibling_name` 的去重行为变化，属于隐性破坏。

### 3.3 没有改的部分（第 16–220 行）

第 16 行之后是七张表的完整 DDL，与课程基线逐字一致。抽查三类关键约束：

- `product.version`：`BIGINT NOT NULL DEFAULT 0` + `ck_product_version CHECK (version >= 0)`，供乐观锁使用；
- `sales_order` 的 6 个 CHECK：支付三字段成组、取消时间、发货时间、完成时间、时间先后顺序；
- `sales_order_item.ck_order_item_amount CHECK (line_amount = unit_price * quantity)`：金额一致性由数据库兜底。

这些约束在 M01-09 会用集成测试逐条验证，不靠"看起来一样"。
