## 2. 这次做了什么

- **上下架**：列表每行一个动作，提交当前 `version`；服务端只接受 `ON_SALE`/`DRAFT`，条件更新 0 行 → 409。
- **增量补货**：列表每行一个小表单（默认 10 件），服务端校验 1–100000，原子累加并返回最新库存；
  溢出时由 `stock <= INT_MAX - qty` 条件挡住，返回 409。
- **页面**：去掉 M07-06 的"随后接入"提示，改成两个真实动作；样式补 `.inline-form` / `.qty-input`。
- **测试**：7 个服务用例、4 个页面用例、1 个 AC-28 并发用例。

**没有做的**：批量上下架、批量补货、补货流水记录（本期不做，PRD 也未要求）。

## 3. 关键设计

### 3.1 上下架也走乐观锁

状态是"别人可能同时在改"的字段：管理员 A 下架、管理员 B 上架，若不带版本，后提交的会静默覆盖。
`WHERE id=? AND version=?` + `version+1` 让后到者拿 409，页面提示刷新（与商品编辑同一口径）。

### 3.2 补货用"累加"而不是"设为"

AC-28 的本质是两条原子更新可以并发：`stock = stock - 2` 与 `stock = stock + 3` 互不覆盖。
若补货写成"读出来 + 写回去"，并发时会丢更新——这正是 FR-A-04 明确要求增量补货的原因。

### 3.3 溢出用 SQL 条件挡住，不靠应用层判断

`stock <= 2147483647 - qty` 写在 `WHERE` 里，数据库保证不会写出负数溢出的库存；
影响 0 行时再读一次区分"商品被删"（404）与"到上限"（409），应用层只做解释。
