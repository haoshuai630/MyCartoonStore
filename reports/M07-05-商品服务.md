## 2. 这次做了什么

在 `catalog` 里补齐后台商品的服务层能力（页面下一任务接入）：

- **列表**：`search(categoryId, keyword, status, page, pageSize)`，含下架商品；分类给一级取子树、给二级精确；关键字按名称包含并转义通配符；按 `id DESC` 分页；一次 JOIN 带出分类名。
- **新增**：SKU（大写、唯一）、名称、二级分类、价格（>0、≤2 位小数、不超 `DECIMAL(12,2)`）、初始库存、简介、描述、封面、排序全校验；状态强制 `DRAFT`。
- **编辑**：只写名称、分类、价格、简介、描述、封面、排序；SKU 与库存不写；`version` 作条件，冲突 409。
- **下拉与回显**：`categoryOptions()` 只列二级（「作品 / 品类」），`filterOptions()` 列一级与二级；`form(id)` 回显价格两位小数与 `version`。

**没有做的**：上下架与补货（M07-07）、商品页面（M07-06）、删除（用下架代替）、相册（M08）。

## 3. 关键设计

### 3.1 价格用字符串接，不用 `BigDecimal` 直接绑

若用 `BigDecimal` 绑定，"12.345" 会走到 `setScale` 才报错、"abc" 会在类型转换阶段抛 `BindException`；
用字符串接后，服务层能给出"必须是数字 / 最多两位小数 / 必须大于 0 / 超出范围"四种明确文案（docs/05 §5 要求字段旁提示）。

### 3.2 版本只在 SQL 条件里生效

`updateProfile` 的 `WHERE id = #{p.id} AND version = #{p.version}` 影响 0 行就是"别人改过"，
不去比较读到的值和提交的值——两步之间仍可能被改，只有数据库条件更新能真正防覆盖（AC-27）。

### 3.3 列表 SQL 与计数 SQL 共用 `adminWhere`

两个查询最容易漂移的地方是筛选条件；抽成一个 `<sql>` 片段后，`selectAdminPage` 与 `countAdminPage` 永远同口径，
分页总数不会与当前页对不上。

### 3.4 下拉只给二级，筛选给两级

商品只能挂二级分类，所以表单下拉只列二级并拼上作品名（避免管理员记编码）；
筛选则允许给一级（看整部作品的全部商品），用缩进区分层级。
