## 1. 这次做了什么

用户端登录成功后先换会话 ID，再写身份——把 docs/01 FR-U-01 里「登录成功后重建 Session（防会话固定）」这条要求补上。
此前只有管理端做了（M07-02），用户端一直沿用登录前的会话 ID，攻击者可以事先把会话 ID 种给受害者，等对方登录后复用同一个 ID。

只换 ID、不换会话：身份写在同一个会话对象上，CSRF 令牌与 `redirect` 参数都不用搬，也与管理端写法同构。

## 4. 关键设计

### 4.1 用 `changeSessionId()` 而不是"销毁后新建"

`invalidate()` + `getSession(true)` 会把 `csrfToken`、`redirect` 全部丢掉，得在控制器里重新搬运；`changeSessionId()` 是 Servlet 3.1 标准的"换 ID 保属性"，
攻击者手里的旧 ID 同样立即失效，防护效果一致，改动面只有一行。管理端 M07-02 已经是这个写法，两端从此同构。

### 4.2 先 `getSession(true)` 再换 ID

正常情况下 CSRF 过滤器已经建过会话，但直接 `POST /login`（不带 Cookie）时也可能没有；先确保会话存在，再 `changeSessionId()`，
避免 `IllegalStateException: Cannot change session ID. There is no session associated with this request.`

### 4.3 令牌存活要有用例兜住

换 ID 最容易踩的坑是"令牌跟着旧会话走了，登录后第一个页面 403"。用例不只断言 ID 变了，还断言：
换 ID 后登录前签发的令牌仍能通过退出请求的校验——把"属性随会话迁移"这件事固定下来。

### 4.4 失败路径完全不动

密码错、账号停用、角色不符都还是回到登录页（200），不换 ID、不建登录态。只有认证成功才轮换，避免给失败请求也发新 ID 的额外复杂度。
