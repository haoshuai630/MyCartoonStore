## 3. 五个关键决策

### 3.1 种子数据用脚本生成，产物是纯 SQL

60 个商品、100 条相册、20 条明细的规则太多（SKU 模板、库存边界、状态分布、净扣库存）。手写必然对不上，脚本可以断言数量。

`db/tools/gen_demo_sql.py` 只负责生成；`02-schema-with-demo.sql` 是纯静态文件，执行端不需要 Python。

### 3.2 订单状态与时间字段成组生成

数据库对 `sales_order` 有 6 条 CHECK：支付三字段成组、取消/发货/完成时间与状态对应、时间先后顺序。手写 10 行很容易漏一个字段，用代码分支生成（`if status in (PAID, SHIPPED, COMPLETED)`）就不可能写出半套。

### 3.3 净扣库存用 UPDATE，不改初始库存

商品段 `stock` 保持"上架库存"语义；订单段之后用 `UPDATE product SET stock = stock - n, version = version + 1` 扣减。取消订单不扣，净影响 0。这与真实下单路径一致，M05 写 Service 时能直接对照。

### 3.4 锁顺序固定：用户 → 车 → 商品（按 id 升序）→ 订单

`ProductMapper.lockByIds` 里 `ORDER BY id`，所有事务同一顺序，不可能形成死锁环。这条在 M05 会被真正使用。

### 3.5 测试用"删表重建"，不用 `@Transactional` 回滚

回滚测试会掩盖事务边界，而 M05 要验证的正是"下单失败整体回滚"。宁可每个用例多花 1 秒。

## 4. 过程中发现的两个问题

### 4.1 Lombok 在 JDK 27 上静默失效（严重）

M01-06 提交实体时构建"成功"，但编译出的类**没有 getter**——JDK 23 起默认关闭隐式注解处理。直到 M01-09 第一次调用 `getProductName()` 才暴露。

修复：父 POM 加 `<proc>full</proc>` + `annotationProcessorPaths`。

**教训**：编译通过不等于代码可用。M01-06 的验收只做到编译，不足。

### 4.2 MySQL CHECK 违规在 Spring 里不是 `DataIntegrityViolationException`

错误码 3819、SQLState `HY000`，被包装成 `UncategorizedSQLException`。断言改成 `DataAccessException` + 消息包含 `Check constraint`。
