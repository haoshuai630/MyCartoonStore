## 3. 五个设计点

### 3.1 快照只是"确认凭据"，不是价格承诺

确认页与提交是两个请求，中间商品可能改价、下架，另一个标签页也可能改车。
所以快照只记录**当时看到什么**（数量、版本、单价），提交时重新读库逐项比对；
不一致就 409 要求重新确认，绝不按快照价成交。

### 3.2 比对前两边都按 `cartItemId` 排序

```java
sorted.sort((a, b) -> Long.compare(a.getCartItemId(), b.getCartItemId()));
```

SQL 没写 `ORDER BY` 时行序不保证；不排序会把"同一辆车、顺序不同"误判成变化，
让用户莫名其妙地被迫重新确认。

### 3.3 价格用 `compareTo`，不用 `equals`

`BigDecimal.equals` 连刻度一起比，`28.0` 与 `28.00` 会判不等。
这里要的是数值相等，所以 `sameAs` 用 `compareTo(...) == 0`；`hashCode` 也先 `stripTrailingZeros`。

### 3.4 确认后 10 分钟内必须提交

`CONFIRM_TTL = Duration.ofMinutes(10)`；`expired()` 用注入的 `Clock` 判断：
`now >= confirmedAt + 10 分钟` 即过期，**恰好第 10 分钟算过期**（时限不含右边界）。

- 没有快照（会话丢失 / 从未确认）也判过期，宁可让用户重新确认；
- `unchanged()` 内再判一次过期，避免调用方只比内容忘了时间；
- 测试用 `Clock.fixed` 覆盖 599 / 600 / 601 秒与 10:11 四个点，不依赖真实时间。

### 3.5 收货字段长度直接对齐列宽

`50 / 30 / 255` 分别对应 `receiver_name / phone / address` 的列宽，超长在服务层就拒，
不让 MySQL 用截断或报错来兜底。电话在"必填 + ≤30"之外只加一条轻校验：**至少含一位数字**，
拦掉纯文字乱填，但仍不限定手机号/座机/国际号的格式。

## 5. 代码注释口径（对齐参考的 Kotlin 测试）

| 文件 | 行数 | 行尾注释 | 覆盖 |
|---|---|---|---|
| `CheckoutService` | 110 | 27 | 25% |

- **package / import / 字段 / 每条语句都有行尾 `//` 注释**，说明"为什么需要它"，不复述代码。
- 方法上方是一句话 `/** ... */`（测试里对应"这个用例验证什么"）。
- 类上方是三行 `//` 说明：依据哪份文档、负责什么、明确不做什么。
- 测试按参考文件的写法：准备、动作、每条断言各自带行尾注释，例如
  `// 另一个标签页把数量 2 改成 3，购物车版本随之 +1`、
  `// 模拟从 Session 取出`、`// 价格按数值比：28.0 与 28.00 是同一个价`。
