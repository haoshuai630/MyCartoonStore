## 3. 关键设计

### 3.1 订单总额由明细算，不手写

```python
total = sum(products[sku]["price"] * qty for sku, qty in items)
```

10 张订单共 20 条明细，手写 `total_amount` 几乎一定会和明细对不上。这里直接从商品价格表算，数据库里再用 SQL 复核（见 §4.3）。

### 3.2 时间用相对 `NOW()` 的表达式

```sql
(DATE_SUB(NOW(), INTERVAL 4 DAY) + INTERVAL 1 HOUR)   -- paid_at
```

不写死 `2026-11-01 10:00:00`，避免"脚本是几个月后跑的，订单时间却停在过去"的尴尬。生成、支付、发货、完成四个时间点按 `created → paid → shipped → completed` 逐级加，天然满足 `sales_order` 的时间顺序 CHECK。

### 3.3 净扣库存用 UPDATE，而不是把初始 stock 直接写成扣减后的值

```sql
UPDATE product SET stock = stock - 2, version = version + 1 WHERE sku = 'STARLINE-C01';
```

两个好处：

- 商品段的 `stock` 仍然是"上架时的库存"，语义清楚；
- 与真实下单路径一致（下单扣、取消恢复），M05 写 Service 时可以直接对照。

取消的两张订单（`0005`、`0010`）不参与扣减，视为"已恢复"，净影响为 0——这也是 03 篇种子规格里写明的口径。

### 3.4 状态与字段成组由代码分支保证

`payment_method / payment_no / paid_at` 三件套只在 `PAID/SHIPPED/COMPLETED` 出现，`cancelled_at` 只在 `CANCELLED` 出现。这是数据库 `ck_order_payment_info` 等 CHECK 的硬约束，手写 10 行很容易漏一个字段，用分支生成就不可能错。

## 4. 验证结果

### 4.1 行数与状态

```
cart_item 10 | sales_order 10 | sales_order_item 20

CANCELLED 2 | COMPLETED 2 | PAID 2 | PENDING_PAYMENT 2 | SHIPPED 2
```

### 4.2 金额一致性

```sql
SELECT o.order_no FROM sales_order o
JOIN (SELECT order_id, SUM(line_amount) s FROM sales_order_item GROUP BY order_id) i
  ON i.order_id = o.id
WHERE o.total_amount <> i.s;
-- 0 行
```

订单总额与明细合计**全部一致**。

### 4.3 库存净扣减

抽查 16 个被扣减的 SKU，全部等于「上架库存 − 未取消订单数量」，`version` 同步 +1：

| SKU | 原库存 | 扣减 | 现库存 |
|---|---|---|---|
| STARLINE-C01 | 12 | 2 | 10 |
| CICADA-C02 | 13 | 2 | 11 |
| IRONWOOD-M02 | 8 | 3 | 5 |
| MISTPORT-C04 | 15 | 1 | 14 |

取消订单涉及的 4 个 SKU **完全未变**：

```
IRONWOOD-C02  13  version 0
CICADA-M05    11  version 0
ONIGIRI-C05   16  version 0
CICADA-C03    14  version 0
```
