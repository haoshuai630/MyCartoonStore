## 2. 这次做了什么

M03 的登录只校验「密码对 + 状态启用」，留下了两个洞：**管理员能从用户端登录并下单**，**登录后被禁用的人继续能操作**。
本任务把身份口径补回来，并为管理端登录准备同一条校验链：

- `AccountService`：`authenticate` 拆成 `authenticateCustomer` / `authenticateAdmin`，共用私有校验；
  失败一律 401 + 「账号或密码错误，或账号不可用」，不再区分"已停用"（原先会返回 403 并提示"账号已停用，请联系店长"）。
- `AuthController`：用户端登录改调 `authenticateCustomer`。
- `LoginInterceptor`：不再只看会话里有没有 `userId`，而是按 id 重读账号，要求「存在 + CUSTOMER + ENABLED」；
  否则 `invalidate()` 旧会话再 302 到登录页——禁用即时生效，管理员会话也不能借用户端购物车。
- `WebConfig`：把 `AccountService` 注入拦截器；重建 `LoginInterceptorTest`（4 → 7 例）与夹具（支持造 ADMIN / DISABLED 账号）。

**没有做的**：管理端登录页与拦截器（M07-02）、会话固定防护的用户端部分（M09 统一）、CSRF（M09）。

## 3. 关键设计

### 3.1 失败"同码同文案"是安全要求，不是体验取舍

账号不存在、密码错、角色不符、已停用四类失败若给不同文案，就等于提供了一个账号/状态探测接口。
统一成 401 + 同一句话后，管理端与用户端共用同一出口，页面上也看不出差别。

### 3.2 每请求重读账号：一次主键查询换取"禁用即时生效"

`store_user` 按主键查一行的成本可忽略，换来的是 FR-U-02 的硬要求：
已持有会话的账号被停用后，**下一个请求**就必须被拒。会话里只留 `userId`/`displayName`，不留角色与状态的快照。

### 3.3 角色判断放在两个入口，而不是拦截器里"猜"

拦截器只认 CUSTOMER：用户端的所有受保护路径都是"顾客行为"。
管理端将来有自己的拦截器（只认 ADMIN），两边各自判断，避免一个布尔值在两端含义不同。

### 3.4 旧会话不合格时作废，而不是只跳转

只跳登录页、不 `invalidate()`，会话里的 `userId` 还在，用户重新访问下一个受保护页会再次被拦，
但若随后账号被恢复，旧会话会"复活"。作废后必须重新登录，符合"禁用即失效"的语义。
