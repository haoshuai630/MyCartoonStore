## 1. 交付内容

| 能力 | 路径 / 类 | 说明 |
|---|---|---|
| 加入购物车 | `POST /cart/items` | 同商品累加，累加后校验 99 与库存；游客拦到登录并回详情页 |
| 购物车页 | `GET /cart` | 行、单价、数量、小计、合计、空车状态、失效条目提示 |
| 改数量 | `POST /cart/items/{id}/quantity` | 1–99、库存、归属、旧版本四道校验 |
| 移除 | `POST /cart/items/{id}/remove` | 带归属与旧版本 |
| 页头徽标 | `CartBadgeInterceptor` | 全部页面注入 `cartCount`，含失效条目，游客 0 |
| 失效条目 | `CartLine` | 下架 / 库存不足给出原因，计入徽标、不计入总额、禁用结算 |

数据层：`CartService`（规则）、`CartLine` / `CartSummary`（视图与汇总）、
`CartItemMapper` 新增 `sumQuantityByUser` / `updateQuantity` / `deleteByIdAndUser`。

## 2. 关键决策

| 决策 | 原因 |
|---|---|
| 校验"累加后"的数量与库存 | 只校验本次输入会出现"每次都对、加起来错" |
| 归属与版本写进 SQL 的 WHERE | 并发下内存比对不可靠；影响 0 行即冲突 |
| 改数量前先查一次归属 | 只有先读到 user_id 才能把 403 与 409 分开 |
| 唯一键冲突退化为累加 | 两个会话同时加同一商品时，不把并发冲突报成 500 |
| 失效判定在查询时算 | 不落库、不后台清洗；库存是随时会变的 |
| 徽标放在拦截器 | 页头被所有页面复用，逐页塞模型必然漏 |
| 游客回跳用 Referer | POST 地址不能直接 GET，否则登录后 405 |
| 状态码按错误码输出 | 403/409 不再被压成 400，验收能区分失败原因 |

## 3. 踩过的坑

| 问题 | 处理 |
|---|---|
| `LoginInterceptorTest` 断言登录后 `/cart` 是 404 | M04-02 改成断言 200，购物车页本身在 `CartPageTest` 断言 |
| 全局异常处理器把所有失败压成 400 | 改成 `e.code().status()`，并补 403/409 用例 |
| 游客加车回跳到 POST 地址 | 同源 Referer 取路径；协议、主机、端口都要对上 |
| Thymeleaf 字符串拼接写错 | 用 `\|有 ${n} 个条目已失效\|` 字面量替换，避免引号与表达式混写 |
| 逐行验收生成器对无注释代码出兜底句 | 新增 `gen_m04_acceptance.py` + `m04_explainer.py`：注释行绿字留空，规则行从代码参数取事实，兜底行清零 |
