> 题目：漫屿 MANGA ISLE —— 原创漫画与官方周边商城（SSM 双端）
> 课程：《软件开发架构平台》实验一（SSM 用户端商城 + 管理端 CMS）

## 1. 项目概况

| 项 | 内容 |
|---|---|
| 业务 | 5 部原创漫画 IP 的单行本与官方周边，单店自营，无多商户 |
| 两端 | 用户端 `:8080`（购物）、管理端 `:8081/admin`（CMS） |
| 技术栈 | JDK 27 / Spring Boot 4.1.2 / Spring MVC / Thymeleaf / MyBatis-Plus 3.5.18 / MySQL 8.4 |
| 形态 | 服务端渲染，无前端框架、无 JSON API（实验二的 REST 另立） |
| 工程 | 一个 Maven 多模块仓库、两个可独立启动的应用、共享七张业务表的库 |
| 规模 | 4 账号 / 5 作品 / 60 分类 / 95 商品 / 160 相册图 / 10 购物车条 / 10 订单 / 20 明细 |
| 验收 | P0 32 条 + P1 2 条（AC-01~34），对应指导书 V01–V18 |
| 测试 | **448 个自动化用例**，10 模块 `mvn clean verify` 全绿 |

课程基线是 MyPetStore（宠物商城）。本项目保留其**全部业务机制**（会话、归属校验、持久化购物车、事务、状态机、乐观锁、并发），
只把业务域平移到漫画与周边；七张表结构一字不改，差异逐条记录在 `docs/08-PRD平移对照表.md`。

## 2. 系统架构

### 2.1 构建结构

```
mycartoonstore/                parent：依赖管理 + 依赖边界检查（maven-enforcer）
├── cartoon-common/            异常、分页、金额、CSRF 过滤器（无 Web starter、无 MyBatis）
├── cartoon-catalog/           分类、商品、相册
├── cartoon-account/           账号、登录校验、资料与改密
├── cartoon-cart/              购物车
├── cartoon-order/             结算快照、下单事务、订单查询、取消
├── cartoon-payment/           模拟支付（依赖 order 的状态机）
├── cartoon-test-support/      测试库重建与测试夹具
├── cartoon-user-web/          用户端应用，8080
└── cartoon-admin-web/         管理端应用，8081，context-path=/admin
```

### 2.2 三条硬规则

1. **单向依赖**：`web → 业务模块 → common`，构建期用 `maven-enforcer-plugin` 拦截反向依赖；
2. **规则只在 Service**：Controller 只做参数绑定、会话取出与跳转，模板不写业务判断；
3. **Mapper 只被本模块 Service 使用**，跨模块取数据必须走对方 Service。

分层与包结构见 `docs/02-概要设计说明书.md` §3–§4。

### 2.3 关键流程

下单是本项目的核心：一次事务内完成「写订单 + 写明细 + 按 SKU 升序扣库存并维护 `version` + 删本次结算条目」，
任一步失败整体回滚；锁顺序固定为「用户行 → 商品（ID 升序）→ 订单」，避免死锁。
支付只改状态与凭证、不重复扣库存；取消只恢复一次库存；发货只允许 `PAID`。

## 6. 关键技术点与取舍

| 主题 | 做法 | 为什么 | 放弃了什么 |
|---|---|---|---|
| 原子下单 | 单事务 + 固定锁顺序 + 按 SKU 升序扣减 | 多明细任一失败必须整体回滚；固定顺序避免死锁 | 分布式事务（单库不需要） |
| 并发控制 | 商品 `version` 乐观锁 + 用户/订单行锁 | 读多写少用乐观锁；同用户/同订单的竞争用行锁串行 | 全表悲观锁（吞吐差） |
| 支付幂等 | 状态条件更新 + 首次凭证不覆盖 | 重复点击与并发重试都不能产生第二张凭证 | 独立幂等键表（超纲） |
| 会话 | 两端各自 Session、Cookie 名不同；登录后 `changeSessionId()` | 一端退出不影响另一端；防止会话固定 | 单点登录 / 集中会话（非目标） |
| CSRF | 同步令牌：过滤器签发 + 29 处表单隐藏域 + 403 页 | 不引 Spring Security 全栈；页面可见、可评审 | 双提交 Cookie / SameSite 兜底 |
| 汇报 | 每个任务一份 Markdown + 一份逐行验收 HTML | 读者能判断"这行为什么非写不可" | 只写"已完成"的流水账 |

逐行验收页由 `db/tools/gen_m0x_acceptance.py` 生成，左列去掉行尾注释、右列一句话说明、不出现「—」；
M01～M04 与 M05 之后的注释规范差异见 `docs/10` §5。

## 7. 踩过的问题与解决

| 现象 | 根因 | 解决 |
|---|---|---|
| 管理端登录后跳到 `/admin/;CARTOON_ADMIN_SESSION=…`，404 | Tomcat 默认允许 URL 跟踪会话，首次登录（尚无 Cookie）把 ID 拼进 302 | 两端 `tracking-modes: cookie`；`docs/02` §5 与 `docs/06` 清单同步 |
| 加 CSRF 后 web 测试全红 | 108 处 POST 没有令牌 | 加 `CsrfTestSupport.csrf()` 统一注入，机械改动 20 个文件 |
| 403 页面在 MockMvc 里断言不到 | MockMvc 不走容器错误分发，`sendError` 只给状态码 | 状态码用 MockMvc 断言，页面文案用 `/error` + `Accept: text/html` 单独断言，真实容器再由探针验证 |
| 「顾客不能登录」用例失败 | 原来断言"失败后无会话"，而 CSRF 令牌本身需要会话 | 改断言"会话里没有 `userId`"，语义不变 |
| AC-28 脚本判 FAIL 但库存明明对了 | `urllib` 自动跟随 302，拿到的是 200 | 判据改成最终 URL（订单详情 / 商品列表）与订单数量 |
| PowerShell 处理脚本时中文变乱码 | `Get-Content`/`Set-Content` 默认编码不是 UTF-8 | 改用 Python 处理含中文的文件；已在汇报里记录教训 |

## 8. 不足与改进

| 不足 | 影响 | 改进方向 |
|---|---|---|
| AC-23 无异常注入用例 | 取消的原子性只有事务设计说明 | 在取消服务上留可注入的故障点，补集成用例 |
| AC-06 无跨端自动化 | 两端会话隔离靠设计与手工 | 起两个应用实例后用 HTTP 脚本断言 Cookie 与登录态互不影响 |
| 无视觉回归 | 样式问题只能人工看图 | 交付前人工在 1366×768 / 1920×1080 各走一遍并截图 |
| 顾客列表内存分页 | 账号上千后变慢 | 下推 SQL 分页 |
| 商品无删除、无图片上传 | 运营能力有限 | 删除用下架代替；上传见 `docs/12` |
