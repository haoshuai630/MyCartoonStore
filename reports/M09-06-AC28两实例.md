## 1. 这次做了什么

docs/06 §3.3 要求 AC-28 必须是**两个应用实例同时运行**的证据，单进程两次调用不算。本任务写了一个取证脚本：
在两个独立 JVM 上分别登录用户端与管理端，用 `Barrier` 同时发出"用户提交订单（买 2 件）"与"后台增量补货（+3 件）"，
再核对库存与订单——初始库存 10，两项都成功时终态应为 11。

结果：库存 11、订单 `CO202611180509436763` 数量 2，**PASS**，两个实例的启动时间与进程号都留在日志里。

## 4. 关键设计

### 4.1 两个 JVM，不是两个端口

用户端与管理端本就是两个可独立启动的应用：脚本分别向 18080 与 18081 发请求，日志里能看到两个不同的进程号
（20720 / 10488）与两个 `Started ...Application` 时间戳（05:09:18 / 05:09:21），这才满足 docs/06 §3.3 的口径。

### 4.2 专用账号，不动种子数据

脚本每次先注册 `ac28`（并清理上次运行的同名账号与其订单），而不是拿 `alice` 做实验。
原因是结算按**整车**下单：`alice` 的购物车里有种子数据，会污染订单金额与明细条数。

### 4.3 `Barrier` 让两个请求真的同时发出

两个线程先各自把页面与令牌准备好（这一步有网络往返，不能算并发），`Barrier.wait()` 之后才发写请求，
保证"下单"与"补货"落在同一个瞬间，而不是先做完一个再做一个。

### 4.4 基线在脚本里重置

每次运行先 `UPDATE product SET stock=10 WHERE sku='CICADA-C01'`，所以脚本可重复执行；
终态断言 `stock == 11` 才有意义，否则第二次跑就变成 19、27……

### 4.5 urllib 会跟 302，判据用最终 URL

第一次运行时把 `302` 当成功判据，结果拿到了 `200`（因为 `urllib` 自动跟随重定向到订单详情页）。
改成"最终 URL 落在 `/orders/{no}` 与 `/admin/products` 上，且订单数量为 2"，这才是用户真正看到的结果。

## 5. 验证结果

```
[setup]   product CICADA-C01 id=77 stock=10（基线）
[user]    注册 ac28 → 200
[user]    登录 → 200
[user]    加入购物车 2 件 → 200
[user]    结算页 → 200
[admin]   登录 → 200
[race]    下单 POST → 200 http://127.0.0.1:18080/orders/CO202611180509436763
[race]    补货 POST → 200 http://127.0.0.1:18081/admin/products
[after]   库存 stock=11（期望 11 = 10 - 2 + 3）
[after]   订单 CO202611180509436763	PENDING_PAYMENT	56.00	2
RESULT: PASS
```

| 检查点 | 期望 | 实际 |
|---|---|---|
| 两实例 | 两个不同进程号与启动时间 | ✅ 20720 / 10488，05:09:18 / 05:09:21 |
| 两项都成功 | 订单创建 + 补货成功 | ✅ 订单号与 `/admin/products` |
| 库存 | 10 - 2 + 3 = 11 | ✅ 11 |
| 订单明细 | 数量 2、金额 56.00（28.00 × 2） | ✅ |
