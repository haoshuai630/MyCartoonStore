## 2. 这次做了什么

给管理端补上"顾客管理"：`/admin/users` 只列用户端注册的顾客（管理员不出现在列表，按 id 直接提交启停也 404），支持用户名包含匹配、启用/禁用筛选、按 ID 升序分页；行内按钮可启用/禁用，禁用前二次确认，重复操作只提示"当前已是…"而不重复写库。控制台从三张卡片扩成四张（2×2），导航加"顾客管理"。

## 4. 关键设计

### 4.1 "只处理顾客"写在服务层，不在页面藏

列表查询固定 `role = CUSTOMER`；启停接口再按 id 查一次角色，`ADMIN` 与不存在的 id 统一 404。页面不渲染管理员只是结果，不是保证——直接构造 POST 也改不了管理员的状态。

### 4.2 内存筛选 + 内存分页

账号总量是教学级（种子 4 个，手工注册也就几十），`selectList` 一次取回后在 Java 里做包含匹配与 `subList`。这样能复用 `LIKE` 转义规则、避免为动态 WHERE 再写一段 XML；分页参数仍走 `PageQuery`（非整数 400、越界页空结果）。若账号上千，再把条件与 `LIMIT` 下推到 SQL——与 M07-10 分类搜索的取舍同一口径。

### 4.3 关键字转义 LIKE 通配符

用户输入 `%`、`_` 按普通字符匹配（先转义反斜杠，再转义 `%` 与 `_`），避免"搜 `%` 命中全部"的意外。长度上限取 `username` 的 50。

### 4.4 只写 `status` 一列

`updateStatus` 是 `UPDATE store_user SET status=? WHERE id=?`；与 M08-01 资料、M08-02 密码一样是定向更新，不整行回写。禁用即时生效不靠"踢会话"，而靠 M07-01 定下的"每个受保护请求重读账号"。

### 4.5 重复操作不是错误

目标状态与当前状态相同时返回 `false`、不写库，控制器提示"该账号当前已是禁用状态"。这比抛 409 更符合后台操作习惯：管理员看到的就是当前状态，不必区分"刚点的"和"之前就是"。

### 4.6 控制台四入口

`entry-grid` 从 3 列改成 2 列，四张卡排成 2×2；导航与 docs/04 §3.1、docs/05 §4.9 同步为四个入口。控制台仍不显示任何统计数字。
