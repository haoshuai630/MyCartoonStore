## 2. 三个设计点

### 2.1 校验"累加后"的值，而不是本次输入

```java
int newQuantity = existing.getQuantity() + added;
if (newQuantity > MAX_QUANTITY) { ... }
ensureStock(newQuantity, product);
```

车里已有 98 件时再加 2 件会被拒；已有 2 件、库存 3 时再加 2 件同样被拒。
只校验本次输入会得到"每次都对、加起来错"的经典问题。

### 2.2 归属与版本写进 SQL，不在内存里比对

```sql
UPDATE cart_item SET quantity = #{quantity}, version = version + 1
WHERE id = #{itemId} AND user_id = #{userId} AND version = #{version}
```

影响 0 行说明"不是本人"或"页面已过期"。为了把这两种情况分成 403 / 409，
修改前先 `selectById` 查一次归属与版本——读取不参与写入，写入仍然由 WHERE 兜底。

### 2.3 并发加车靠唯一键兜底

`uk_cart_user_product` 保证同用户同商品只有一条。两个会话同时加同一商品时，
后插入的一方会拿到 `DuplicateKeyException`，这里退化为"已存在则累加"重试一次，
而不是把唯一键冲突变成 500。种类上限（20）只做普通计数校验，不追求跨会话严格串行：
它的后果是多一辆车有 21 种商品，不影响金额与库存正确性。
